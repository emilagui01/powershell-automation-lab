#region Overview

The first two labs built a Windows domain and a help desk to support it. This lab automates the work that help desk does most often: setting up accounts for new hires, shutting off access when someone leaves, and checking which accounts need attention.

Every script previews its changes with -WhatIf before making them, logs every action, and is safe to run twice. Each real run is tied to an osTicket ticket number, which is written onto the account in AD. Anyone looking at an account later can find the request behind it.

PhaseScriptWhat it does
1. OnboardingNew-LabUsers.ps1Reads a CSV of new hires; creates each account in its department OU, adds groups, and builds a private H: drive
2. OffboardingRemove-LabUser.ps1Disables, strips group access, moves to Disabled Users, archives the home folder; refuses protected accounts
3. ReportingGet-LabUserReport.ps1Finds locked out, disabled, never-used and password-problem accounts; writes HTML and CSV
4. TicketsosTicket + all threeHR requests arrive as tickets; scripts run with the ticket number; results go back on the ticket

Skills: PowerShell scripting (advanced functions, SupportsShouldProcess, error handling, pipeline input), the ActiveDirectory module, NTFS and share permissions with icacls and New-SmbShare, user lifecycle (joiner, leaver), audit logging, reporting, and ITSM workflow.

New-LabUsers.ps1 ✕

#region Phase 1: Onboarding

One command turns a CSV from HR into working accounts. For each row the script:

  1. Checks the row: first and last name present, department one of IT, HR, Finance, Marketing
  2. Skips anyone who already has an account, matching on first and last name or display name, and flags them for a person to review
  3. Builds a unique username: first initial + last name, letters and numbers only, with a number added if taken (jsmith → jsmith2)
  4. Creates the account in the department OU with a random 12-character temporary password and change password at next sign-in
  5. Adds it to GRP-<Department> and Lab Staff
  6. Creates \\DC01\Home$\<username>, grants only that user Modify, and maps it as H:
  7. Writes a log, a results CSV, and a separate password handoff file meant to be deleted after use

Remove-LabUser.ps1 ✕

#region Phase 2: Offboarding

When someone leaves, the account is locked down and kept, not deleted. Deleting loses the account's ID, its group history and its files, and can't be undone if HR made a mistake. For each username the script:

  1. Refuses protected accounts: Administrator, krbtgt, Guest, any Domain Admins member, anything in Service Accounts
  2. Logs the user's groups before removing them, so access could be restored
  3. Disables the account and resets the password to a random 32-character value
  4. Removes every group membership
  5. Stamps the Description: Disabled 2026-10-01 by Administrator - Ticket #125558
  6. Moves it to OU=Disabled Users, where the Lab 1 policies no longer apply
  7. Moves the home folder to an admin-only archive and clears the H: mapping

#What the report found

  • Two accounts whose password never expires: Administrator and svc-osticket. That's common for service accounts, and exactly what a report like this is meant to surface. The better fix is a group Managed Service Account, whose password Windows rotates automatically.
  • Lab 1 accounts have no Department. jdoe, jsmith and pparker were made by hand and show blank. Accounts made by the script always have it filled in.
  • The numbers reconcile. Between the first and final reports, Never signed in went 14 → 15: Stephen and Hope added, Wanda moved to Disabled. Must change password went 13 → 14 the same way.
Why "inactive" uses 30 days: LastLogonDate comes from lastLogonTimestamp, which AD only updates every 9 to 14 days by design. It's accurate for "inactive for a month," not for "signed in today."

75function Write-Log {
76    param(
77        [Parameter(Mandatory)][string]$Message,
78        [ValidateSet("INFO", "OK", "WARN", "ERROR")][string]$Level = "INFO"
79    )
80    $line = "{0} [{1}] {2}" -f (Get-Date -Format "yyyy-MM-dd HH:mm:ss"), $Level, $Message
81    Add-Content -Path $LogFile -Value $line -WhatIf:$false
82    $color = @{ INFO = "Gray"; OK = "Green"; WARN = "Yellow"; ERROR = "Red" }[$Level]
83    Write-Host $line -ForegroundColor $color
84}

97function Get-UniqueSamAccountName {
98    # First initial + last name, lowercase, letters and numbers only, max 20 characters.
99    # If taken (in AD or earlier in this run), append 2, 3, 4...
100    param([string]$First, [string]$Last)
101    $base = (($First.Substring(0, 1) + $Last).ToLower()) -replace '[^a-z0-9]', ''
102    if ($base.Length -gt 18) { $base = $base.Substring(0, 18) }
103
104    $sam = $base
105    $n   = 1
106    while ($Reserved.Contains($sam) -or (Get-ADUser -Filter "SamAccountName -eq '$sam'")) {
107        $n++
108        $sam = "$base$n"
109    }
110    [void]$Reserved.Add($sam)
111    return $sam
112}

114function New-TempPassword {
115    # 12 characters with at least one upper, lower, digit and symbol, so it always meets
116    # domain complexity. (If New-ADUser's password is rejected, the account is still
117    # created but left disabled - see Lab 1, troubleshooting.)
118    # Ambiguous characters (0/O, 1/l/I) are left out so it can be read aloud.
119    $upper = "ABCDEFGHJKLMNPQRSTUVWXYZ"
120    $lower = "abcdefghijkmnopqrstuvwxyz"
121    $digit = "23456789"
122    $sym   = "!@#$%*?"
123    $all   = $upper + $lower + $digit + $sym
124
125    $chars = @(
126        $upper[(Get-Random -Maximum $upper.Length)]
127        $lower[(Get-Random -Maximum $lower.Length)]
128        $digit[(Get-Random -Maximum $digit.Length)]
129        $sym[(Get-Random -Maximum $sym.Length)]
130    )
131    $chars += 1..8 | ForEach-Object { $all[(Get-Random -Maximum $all.Length)] }
132    return -join ($chars | Sort-Object { Get-Random })
133}

#Design choices

ChoiceWhy
[CmdletBinding(SupportsShouldProcess)]Gives every script a real -WhatIf. Every change sits behind $PSCmdlet.ShouldProcess(), while logging uses -WhatIf:$false so a dry run still leaves a record.
try / catch per userOne bad account fails on its own line without stopping the rest of the batch.
Duplicate check before createMakes onboarding safe to re-run. Same name means probably the same person, so a human decides.
Passwords built to meet complexityIf New-ADUser rejects a password, it still creates the account, but disabled, a lesson from Lab 1. Each temporary password is guaranteed one upper, lower, digit and symbol.
Handoff file kept separate from the logLogs are kept; passwords are not. The handoff file is deleted after the passwords are handed out.
Offboarding disables, never deletesReversible, auditable, and keeps the account's SID and files for a manager or legal hold.
Pipeline input on -Identity"slang","wmaximoff" | .\Remove-LabUser.ps1 -Ticket 125558 works for batches.

A pipeline pasted into the ISE console ran in two halves # ISE console, DC01
Symptom A multi-line command pasted into the console ran its first line on its own, then threw a parser error on the leftover fragment.
Cause The ISE console runs each pasted line as soon as it is complete. A line that ends in | waits for more, but a line that doesn't is run immediately.
Fix Commands typed in the console were kept to one line. Anything longer went into the script pane and was run with F8 (Run Selection).
Duplicate check missed an existing user: Peter Parker # New-LabUsers.ps1
Symptom The first version of the duplicate check would have created a second account for Peter Parker, who already existed as pparker.
Cause The check matched on GivenName and Surname. pparker was created by hand in Lab 1 with only a display name, so both fields were empty.

Symptom While testing Bruce's first sign-in, the password handoff list was open in the DC01 console behind the CLIENT01 window, and it showed up in the screenshots.
Cause The handoff file had been opened in the console to read Bruce's password, and the window was left open.
Fix Those screenshots were cropped to the CLIENT01 window before publishing, and the handoff file was deleted once it had been used. In production, temporary passwords go to the new hire's manager over a secure channel, or the user sets their own through self-service password reset.
